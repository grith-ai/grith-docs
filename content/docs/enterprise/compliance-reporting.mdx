The compliance feature produces auditor-ready bundles from grith's audit log,
shaped to match common compliance framework expectations.

## Frameworks supported

Each framework has a dedicated export shape:

| Framework | Focus | Export shape |
| --- | --- | --- |
| **SOC 2 Type II** | Control objective + evidence period | CSV evidence sheet + summary PDF |
| **ISO 27001** | Annex A control mapping | JSON bundle per control |
| **GDPR** | Data processing register | CSV per data-flow |
| **HIPAA** | Access log + risk events | CSV + access timeline |
| **PCI-DSS** | Cardholder-data egress events | JSON + filtered audit log |

## What's in a bundle

Each export includes:

- **Decision counts** by control objective.
- **Canary fires** with full timeline.
- **Threshold change history** — who changed what threshold when.
- **Policy edits** — full audit of policy lifecycle.
- **Notification delivery records** — proof that alerts were sent.
- **Incident response timelines** — when canaries fired, when sessions were
  terminated, when the team reviewed.

## Generating

From the dashboard:

1. **Compliance → New report**.
2. Pick framework, time window, scope (entire team or specific projects).
3. Click **Generate**. Reports run async; you get a notification when ready.

From the API:

```
GET /analytics/compliance?framework=soc2&since=2026-01-01&until=2026-03-31
```

Returns a signed bundle (JSON + CSV) downloadable via a one-time link.

## Retention

Cloud-held analytics are retained for **90 days** — rollups, security events and
the active analytics archive alike. Raw audit records are never uploaded; they
stay on each developer's device (local SQLite, retention per
[`audit.retain_full_days`](/docs/ops/logging-and-audit-retention)). See
[Analytics & cost](/docs/pro/analytics-and-cost) for the full retention table.

Anything that has to outlive 90 days must be exported and retained by you;
`grith audit export` writes the device's own records to JSON or CSV.

## Integrity

Exports are **not** cryptographically signed, and grith does not publish a
verification key. What integrity evidence exists is different in each place,
and the distinction matters to an auditor:

- **On the device**, audit records form a hash chain. Any edit or deletion
  inside the retained window breaks the chain, which `grith audit diagnose`
  reports, so the local log is tamper-evident.
- **In the cloud**, analytics archives are checksum-verified: the server checks
  an uploaded object's size, SHA-256 checksum, encryption and key identity
  before it becomes the active archive for a day. That establishes the object
  is the one the device declared — not that it is immutable or signed.

Describe grith's evidence to auditors in those terms rather than as a signed
artefact.

## Custom controls

For frameworks not in the built-in set, Enterprise customers can author
custom control mappings:

```toml
[compliance.custom.acme-internal-policy]
description = "Internal acme controls"
controls = [
    { id = "CTRL-1.1", grith_filters = ["canary", "dlp-gate"], objective = "no exfil" },
    { id = "CTRL-2.3", grith_filters = ["capability"], objective = "least privilege" },
]
```
