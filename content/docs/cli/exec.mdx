```
grith exec [OPTIONS] -- <COMMAND> [ARGS...]
```

Spawn `<COMMAND>` (or attach to an existing PID) under grith's syscall-level
supervisor. Every interesting syscall the process tree makes routes through the
filter pipeline before execution.

This is the workhorse command — almost every real grith session starts with
`grith exec`.

## Synopsis

```
grith exec [--profile <NAME>]
           [--attach <PID>] [--allow-queued] [--workspace-only]
           [--syscall-log <FILE>] [--trace-syscalls-jsonl <FILE>]
           -- <COMMAND> [ARGS...]
```

The double-dash (`--`) is required when the supervised command has its own flags. It
tells `grith` where its options stop and the target command's begin.

## Options

| Flag                            | Type   | Default   | Description                                                                                                                                                                                        |
| ------------------------------- | ------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--profile <NAME>`              | string | `generic` | Supervisor profile to use. See [Choose your agent](/docs/start/choose-your-agent).                                                                                                                 |
| `--attach <PID>`                | u32    | —         | Attach to an existing process by PID instead of spawning. Useful for already-running agents.                                                                                                       |
| `--allow-queued`                | flag   | off       | In a non-interactive session (no terminal), allow and log queued operations instead of the default fail-closed auto-deny. No effect in an interactive session, where the approval dialog is shown. |
| `--workspace-only`              | flag   | off       | Deny file reads and writes outside the workspace instead of scoring them. See [Workspace-only sessions](#workspace-only-sessions).                                                                 |
| `--syscall-log <FILE>`          | path   | —         | Log every syscall request and decision to a file (human-readable).                                                                                                                                 |
| `--trace-syscalls-jsonl <FILE>` | path   | —         | Write raw pre-filter syscall forensics to a JSONL file. Heavyweight; use for forensics.                                                                                                            |

## Examples

Spawn Claude Code with the matching profile:

```
grith exec --profile claude-code -- claude
```

Wrap a plain bash session:

```
grith exec --profile generic-cli -- bash
```

Fence a session to the project you launched it in:

```
cd ~/projects/some-repo
grith exec --workspace-only --profile claude-code -- claude
```

Attach to an already-running Python REPL:

```
grith exec --attach 17421
```

(The target must be a descendant of a process you can ptrace. See
[Installation: permissions](/docs/start/installation#permissions).)

Forensic record-and-replay:

```
grith exec \
    --profile claude-code \
    --trace-syscalls-jsonl ~/.cache/grith/last.jsonl \
    -- claude

# Later, audit the recorded session against the profile:
grith profile audit --profile claude-code --trace ~/.cache/grith/last.jsonl
```

## What it does, in order

1. Connects to the local daemon, auto-starting one if none is running. If it cannot
   establish a trusted, version-compatible daemon connection, `grith exec` fails closed:
   it refuses to start the supervised session and exits non-zero. There is no in-process
   or no-daemon fallback.
2. `fork()` the target process. The child calls `ptrace(PTRACE_TRACEME)` to be traced
   by the parent, then installs its own seccomp filter.
3. Child `execve()`s the target binary, which raises a ptrace exec-stop.
4. The parent catches the exec-stop, sets its ptrace options, resumes the child, and
   the supervisor takes over.
5. Every interesting syscall (configured set: file ops, exec, sockets, network) traps
   to the supervisor.
6. The call shape is sent through the filter pipeline.
7. Decision (`ALLOW` / `QUEUE` / `DENY`) is applied via `ptrace(PTRACE_SYSCALL)` or
   register rewriting.

## Workspace-only sessions

By default the workspace is a _trusted_ region: paths inside it are trusted,
paths outside it are scored, and a low-scoring read outside it is auto-allowed
without a prompt. `--workspace-only` makes it a _boundary_ instead. A file read
or write whose target is outside the workspace is denied rather than scored —
including the read-only opens `[supervisor.noise_reduction] ignore_read_only`
waves through today.

The workspace is:

- the directory you ran `grith exec` in,
- every linked git worktree of that repository (`[supervisor.trust]
include_linked_worktrees`, on by default — the main worktree included, so
  launching from a subdirectory covers the repository root; a worktree git
  reports still has to pass the checks described under
  [`[supervisor.trust]`](/docs/config/supervisor#workspace-trust)),
- anything listed in `[supervisor.trust] additional_project_roots`.

Your other projects, the rest of your home directory, `/mnt`, `/media` and
`/srv` are not in it.

Three things stay reachable, because the supervised tool could not run
otherwise:

1. **Noise paths** — `/proc`, `/sys`, the terminal, CA certificates.
2. **Reads of system runtime paths** — `/usr`, `/lib`, `/bin`, `/etc`,
   `/opt`, `/nix/store` and similar. A tool that cannot read `libc` does not
   start. _Writes_ into those trees are still refused. Resolver configuration
   written at runtime is included (`/run/systemd/resolve/`,
   `/run/resolvconf/`, `/run/NetworkManager/`, `/run/nscd/`) because
   `/etc/resolv.conf` is a symlink into one of them on most Linux systems and
   the resolver opens the target — without it the session cannot do DNS at
   all. The rest of `/run` is not exempt: `/run/user/<uid>` holds your
   keyring, gnupg and ssh-agent sockets.
3. **The paths your profile declares routine** — `~/.claude`,
   `~/.nvm/versions/**`, `/tmp/<tool>-*` and the rest of the profile's
   `routine_paths`. The mode restricts a tool; it does not sabotage one.

<Callout type="info">
  The boundary only ever **removes** access. Each exemption above means "the boundary does not
  decide this call" — never "allow it". The call still goes through the whole filter pipeline
  afterwards, so a read of `/etc/shadow` is exempt from the boundary and still denied by the
  secret-scanning filters.
</Callout>

Refusals are recorded in the audit log as `workspace_only_blocked`, so a tool
that stops working reads as restricted rather than broken. If something
legitimate is outside the fence, add it to `additional_project_roots` rather
than turning the mode off.

<Callout type="warning">
  **Agent config in parent directories stops being visible.** Coding agents look for their
  configuration by walking up from the working directory — Claude Code reads `CLAUDE.md` and
  `.claude/rules` at every level above the project, and others do the same. Those ancestors are
  outside the workspace, so a workspace-only session sees the project's own config and nothing above
  it. That is the mode doing its job, not a fault; if you keep shared instructions in a parent
  directory, name that directory in `[supervisor.trust] additional_project_roots`.
</Callout>

To see what a session refused:

```
grith audit --session <id> | grep workspace_only_blocked
```

The same posture is available permanently as `[supervisor.trust]
restrict_to_workspace = true`. There is deliberately no `--no-workspace-only`:
a flag that could loosen a configured boundary would let anything able to
invent a command line undo it.

## PTY forwarding

For interactive targets (REPLs, shells, TUI agents) grith allocates a PTY pair and
shuttles bytes transparently. Input editing, ANSI escapes, and signals (Ctrl-C,
Ctrl-Z) work exactly as if grith weren't in the loop.

### Scrolling and copy-paste

The supervisor TUI captures the mouse so the **scroll wheel** drives grith's
scrollback (otherwise the host terminal turns the wheel into arrow keys that
agents reject). Mouse capture also means a plain click-drag selection is owned by
grith, so the keys below switch between scrolling and selecting:

| Key                         | Action                                                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `Shift+PgUp` / `Shift+PgDn` | Scroll the terminal scrollback.                                                                                                            |
| `Ctrl+T`                    | **Toggle select mode** — drops mouse capture and freezes the screen so you can drag-select and copy text. Press again to resume scrolling. |
| `Ctrl+L`                    | Toggle the audit-log panel.                                                                                                                |

While select mode is on, the footer shows
`SELECT MODE — drag to copy · wheel-scroll paused`, and repaints are frozen so
your selection isn't wiped by live output. A permission prompt overrides the
freeze so a queued decision is never hidden.

## Exit behaviour

- Exits with the target's exit code when the target exits normally.
- Sends SIGTERM to the supervised tree on Ctrl-C; SIGKILL after a 5s grace period.
- Records the session-end event in the audit log.
